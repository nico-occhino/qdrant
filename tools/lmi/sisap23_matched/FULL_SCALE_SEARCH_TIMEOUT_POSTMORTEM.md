# SISAP23 LMI full-scale search timeout: diagnostic postmortem

**Status:** the retained full-scale index is unaccepted but remains a strong recovery candidate. Job `24991758` reproduced the cold-NFS timeout with a real SISAP warmup query and showed that the same request succeeds after an inventory read. This confirms cold-versus-warm behavior for one query, but does not establish whether the project's 20 official warmup queries sufficiently prepare representative measured queries. The failed stage and accepted Plain generation remain preserved. No rebuild or publication has occurred.

## Executive summary

PBS job `24900597.pbs-m1.metacentrum.cz` completed the expensive construction and persistence-copy stages, then failed during ordinary collection-search validation. It did not publish a generation. The decisive error was a 60-second timeout in `Collection.search()` on a one-hot 768-dimensional query. Before that call, the verifier had checked the live indexed population and persisted LMI metadata. Because the timed-out call returned an error, its expected IDs and post-search learned/fallback counter checks never ran.

The failed artifact was copied, by inventory-verified read-only operations, to disposable diagnostic workspaces under `development-search-timeout-24900597-20261026`. A PBS diagnostic compiled commit `9b12d583b1bf9df802b2cc420244bd3c24732d86` plus test-only instrumentation (patch SHA-256 `5da309f874ac11f57cdfe8b0aa15746cc88296121028841dbe80315ae88e694a`). On the scratch-local copy, the exact ordinary query finished in 55 ms: one learned route, zero Plain fallbacks, 14,764 candidate offsets, about 6.7 ms routing and 48 ms candidate scoring. On an isolated persistent NFS copy after `POSIX_FADV_DONTNEED`, it timed out at 60.08 s: one learned route, zero fallback, the same selected buckets and candidate count, about 7.7 ms routing, and no completed scoring result at the counter snapshot. The process used about 3% CPU and incurred 8,525 major faults. This reproduces a cold persistent-storage candidate-vector access bottleneck; it does **not** prove that the earlier job had the same cache state or exact causal path.

The current evidence supports an I/O/page-fault bottleneck during exact scoring of routed candidates on cold persistent NFS storage, rather than a router delay or silent Plain fallback. The candidates are modest in count, but their vectors are accessed through the persistent vector store and can cause many random file-backed reads. The same one-hot query passed in 71.8 ms after a sequential inventory read warmed the copy, with identical IDs to the scratch run. Do not mask this behavior by merely increasing the 60-second timeout or by validating only an easier query. The workload-specific cold/warm experiment below is still necessary because the verifier's one-hot input is not drawn from the benchmark's query distribution.

## Topology context and prior correction

Qdrant stores a collection as a segment holder. Segment directories on disk are physical persistence artifacts; the holder's membership is the authoritative set of active segments. Optimizer replacement may leave an obsolete directory on disk until cleanup or flush. Therefore two nonempty-looking directories do not necessarily mean two active segments. Conversely, a target optimizer segment count of one is a merge goal, not a guarantee that one active segment has been produced at every observation point. The old verifier's `locate_segment()` logic that demanded exactly one nonempty persisted segment conflated physical paths and live holder topology.

The earlier lifecycle work corrected that assumption with explicit active-versus-persisted accounting and a two-active-LMI-segment ordinary collection-search test. Development evidence at `development-24893548.pbs-m1.metacentrum.cz` records all nine synthetic tests passing. In its 64-point case, the collection query returned cross-segment top-k IDs `[33, 1]`, both segment-local learned-route counters advanced, Plain fallback stayed at zero, and the behavior survived flush/restart. This establishes the tested small-scale topology and merge semantics; it does not establish 10M-point cold-storage latency.

## Search path and observed behavior

At collection level, `lib/collection/src/collection/search.rs` dispatches the request into `collection_manager/segments_searcher.rs`. That searcher obtains active segments from the holder, schedules segment searches, and aggregates each segment's scored results into the collection top-k. The LMI correction supports one valid router/postings state per active LMI segment; segment offsets are local, then Qdrant's segment/collection mappings return public point IDs.

In `lib/segment/src/index/lmi_index/mod.rs`, `LmiIndex::supports_candidates()` accepts the unfiltered dense nearest query used here when parameters are absent/default, quantized vectors are not active, and a routing state exists. `LmiIndex::search()` calls `routing_state.candidates_for_query()`, then `score_candidates()`. Unsupported query forms can use the Plain fallback, but the diagnostic counter proves the tested one-hot request did not take it.

`lib/segment/src/index/lmi_index/routing.rs` selects the top `nprobe` buckets, concatenates postings, sorts and deduplicates local offsets. The reported query selected buckets `[298, 822, 2087, 2176]`, with posting lengths `[1756, 5972, 1031, 6005]`, producing 14,764 unique candidate offsets. `lib/segment/src/index/candidate_scoring.rs` filters invalid/deleted/deferred offsets and invokes Qdrant's `BatchFilteredSearcher` over the vector store to compute authoritative scores and retain top-k. The candidate count and route duration make router inference an unlikely explanation for the observed minute; exact candidate vector reads are the key phase to investigate.

### What the actual benchmark warmups establish

The prepared query root is `sisap23-independent-matched-20261019-01`; its manifest identifies `queries_warmup.f32le` as 20 vectors. In `lib/collection/src/tests/lmi_sisap23_matched.rs`, evaluation loads those 20 vectors and calls `search_one` before measured rows. For LMI, `search_one` directly selects router buckets and invokes `score_candidates` on the segment; it does not call ordinary `Collection.search()`. The warmup loop discards returned IDs, candidate counts, and durations. `run_setting()` repeats the 20 warmup calls for each parameter setting and likewise records no warmup timings. Thus the existing protocol specifies warmup inputs, but its evidence does not show whether any of the 20 calls is slow or whether row 20 is fast after those calls.

Job `24991758` tested only row 0 twice, with a full inventory scan between cold and warm queries. It did **not** run the official 20-query warmup sequence. It therefore confirms the persistent cold-read mechanism but cannot answer warmup sufficiency. The next diagnostic must execute all 20 prepared queries in order, retain each latency, returned IDs, candidate count and errors, and then run at least measured row 20. It must not use a full inventory scan as warmup. It should also issue an ordinary `Collection.search()` after those 20 queries and retain per-segment learned/fallback counter deltas. Any slow or failed warmup row must remain visible.

### Current recovery acceptance contract

`recovery_stages.construct()` makes an isolated scratch copy, verifies its inventory, builds the index, copies the result to a new persistent staging directory, and invokes `sisap23_recovery_verify` against that persistent path. That Rust verifier audits points and mappings, performs two normal restarts, checks vector fingerprints and index-file hashes, checks persisted index/postings/topology, then calls `verify_normal_lmi_query()`. That query is an ordinary collection search with no explicit warmup and the default approximately 60-second operation timeout. A timeout makes the Rust test fail; `recovery_stages.rust()` then refuses a report, metadata creation and publication. `generation_publication.review_staging()` and `check_generation_metadata()` also require a successful `persistent_report.ordinary_lmi_query_path` with per-segment learned-route and zero-fallback evidence. This is an intentional fail-closed contract, but it combines persistent-byte/structure integrity with cold-NFS first-query latency.

The 20 existing warmup calls do not satisfy this requirement: they are unmeasured direct segment-index calls, not the ordinary API proof, and they are not part of `sisap23_recovery_verify()`. A byte-identical scratch copy alone also does not satisfy the current contract because the required ordinary-query evidence is explicitly in the persistent report. I recommend an explicit evidence-schema revision rather than removing the check: retain strict persistent source/copy SHA-256 inventory and post-copy rehash; perform structural reopen, restart and query correctness on a verified isolated copy; store a separate persistent-NFS cold-query report that may record a timeout as an operational limitation; record all 20 official warmup timings/errors and measured-query results on the same node/filesystem; and require ordinary collection-search learned-route counters with zero fallback after that actual warmup. A scratch-local query report may supplement this evidence, but must be labeled local scratch and cannot replace NFS observations or be compared against a cold NFS baseline. This contract change should be implemented only after the 20-query diagnostic confirms its behavior and Python tests enforce every required report field.

## Recovery decision and safety

The preserved full-scale stage has a strong integrity record and apparently complete built structures, but the ordinary query proof failed. Do not mark it accepted or run a publisher against it. Revalidation must use a new disposable copy and the normal acceptance contract. The one-hot cold-copy diagnostic exceeded the configured timeout, while a full inventory warmup made the same request fast and preserved identical index hashes. This establishes that the artifact can serve that query when its vector pages are resident, but it does not resolve first-query behavior or prove the historical job's cache condition. The prepared SISAP query comparison will show whether the same issue affects the actual evaluation distribution.

Both the accepted Plain source and retained failed staging path are read-only. Diagnostic copies and reports are under the separately named development root. No full rebuild has been submitted. No matched baseline benchmark has been run.

After authenticated SSH access is restored, retrieve and verify all raw records from PBS job `24991758` (including resource usage and exact hash values). Then run a bounded diagnostic of the complete 20-query official warmup sequence, logging every query and the first measured row; do not insert a full inventory scan. If a safe copy cannot be established, stop. A fresh 10M construction is unjustified while the same persistence-query behavior remains unresolved.
